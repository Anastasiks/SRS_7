# StudyFlow — структура базы данных

## 1. Общая информация

StudyFlow использует Django ORM для работы с базой данных. В локальной конфигурации применяется SQLite. При развёртывании на Render проект можно подключить к PostgreSQL через переменную окружения `DATABASE_URL`.

Основные модели приложения `dashboard`:

- `Project` — проект, объединяющий задачи.
- `Task` — задача с исполнителем, владельцем, статусом и приоритетом.
- `Activity` — запись об изменении или событии, связанном с задачей.

## 2. Схема связей

```text
┌─────────────────────┐
│       Project       │
├─────────────────────┤
│ id                  │
│ name                │
│ description         │
│ created_at          │
└──────────┬──────────┘
           │ 1
           │
           │ N
┌──────────▼──────────┐
│        Task         │
├─────────────────────┤
│ id                  │
│ title               │
│ description         │
│ project_id          │
│ owner_id            │
│ assignee_id         │
│ status              │
│ priority            │
│ deadline            │
│ rejection_reason    │
│ created_at          │
└──────────┬──────────┘
           │ 1
           │
           │ N
┌──────────▼──────────┐
│       Activity      │
├─────────────────────┤
│ id                  │
│ task_id             │
│ event_type          │
│ description         │
│ actor_id            │
│ created_at          │
└─────────────────────┘
```

Дополнительные связи с таблицей пользователей Django:

- `Task.owner_id` — владелец задачи.
- `Task.assignee_id` — назначенный исполнитель.
- `Activity.actor_id` — пользователь, выполнивший действие.

## 3. Описание моделей

### 3.1. Project

| Поле | Тип | Назначение |
|---|---|---|
| `id` | AutoField | Первичный ключ |
| `name` | CharField(200) | Название проекта |
| `description` | TextField | Описание, необязательное |
| `created_at` | DateTimeField | Дата и время создания |

Связь: один проект может содержать несколько задач.

### 3.2. Task

| Поле | Тип | Назначение |
|---|---|---|
| `id` | AutoField | Первичный ключ |
| `title` | CharField(200) | Название задачи |
| `description` | TextField | Описание, необязательное |
| `project_id` | ForeignKey | Проект задачи |
| `owner_id` | ForeignKey | Владелец задачи, может быть пустым |
| `assignee_id` | ForeignKey | Исполнитель, может быть пустым |
| `status` | CharField(20) | Текущий статус |
| `priority` | CharField(10) | Приоритет |
| `deadline` | DateField | Срок выполнения, может быть пустым |
| `rejection_reason` | TextField | Причина отклонения |
| `created_at` | DateTimeField | Дата и время создания |

Статусы задачи:

- `new`
- `pending`
- `assigned`
- `rejected`
- `in_progress`
- `done`

Приоритеты:

- `low`
- `medium`
- `high`

При удалении проекта связанные задачи удаляются согласно `on_delete=models.CASCADE`.

При удалении пользователя-владельца его задачи удаляются согласно настройке `CASCADE`. При удалении назначенного исполнителя поле исполнителя становится пустым благодаря `SET_NULL`.

### 3.3. Activity

| Поле | Тип | Назначение |
|---|---|---|
| `id` | AutoField | Первичный ключ |
| `task_id` | ForeignKey | Связанная задача, может быть пустой |
| `event_type` | CharField(20) | Тип события |
| `description` | CharField(255) | Описание события |
| `actor_id` | ForeignKey | Пользователь-инициатор, может быть пустым |
| `created_at` | DateTimeField | Дата и время события |

Типы событий включают создание, отправку, подтверждение, отклонение, назначение, начало, завершение, обновление и удаление задачи.

Если задача удаляется, запись истории сохраняется, а ссылка на задачу становится пустой благодаря `SET_NULL`. Аналогично, при удалении пользователя-инициатора ссылка на него становится пустой.

## 4. Целостность данных

В моделях используются внешние ключи для связи проектов, задач и пользователей.

Для изменения статусов реализована серверная проверка допустимых переходов. При выполнении перехода статус задачи и запись истории сохраняются в рамках транзакции, что помогает избежать частичного изменения данных.

## 5. Применение миграций

Для применения миграций используется команда:

```powershell
python manage.py migrate
```

Для проверки наличия изменений в моделях:

```powershell
python manage.py makemigrations --check --dry-run
```

Для локальной разработки используется SQLite. При подключении PostgreSQL на Render будет создана отдельная база данных. Данные из локального `db.sqlite3` автоматически в PostgreSQL не переносятся.

## 6. Примечание

Схема отражает модели `Project`, `Task` и `Activity` из приложения `dashboard`. Системные таблицы Django, например пользователи, группы, сессии и журнал администратора, в схему не включены.# StudyFlow — структура базы данных
