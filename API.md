# StudyFlow — документация REST API

## 1. Общая информация

StudyFlow — веб-приложение для управления проектами и задачами. REST API позволяет получать информацию о проектах, создавать и изменять задачи, управлять их статусами и просматривать историю изменений.

Базовый адрес локального сервера:

`http://127.0.0.1:8000`

API реализован с помощью Django REST Framework.

### Формат данных

REST API использует JSON для передачи данных.

Для запросов, изменяющих данные, применяются соответствующие HTTP-методы: POST, PUT, PATCH и DELETE.

### Аутентификация и доступ

Для REST API используются права доступа `IsAuthenticated`. Перед выполнением запросов необходимо войти в систему.

Для авторизации через браузер доступен интерфейс:

`/api-auth/`

Доступ к задачам ограничен задачами текущего пользователя. История изменений также фильтруется с учётом доступных пользователю данных.

## 2. Основные маршруты

### 2.1. Задачи

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/tasks/` | Получить список доступных задач |
| POST | `/api/tasks/` | Создать задачу |
| GET | `/api/tasks/{id}/` | Получить задачу по ID |
| PUT | `/api/tasks/{id}/` | Полностью обновить задачу |
| PATCH | `/api/tasks/{id}/` | Частично обновить задачу |
| DELETE | `/api/tasks/{id}/` | Удалить задачу |
| POST | `/api/tasks/{id}/transition/` | Изменить статус с проверкой допустимости перехода |

`{id}` — идентификатор задачи.

При создании задачи через REST API владелец определяется по текущему пользователю. Поля владельца, статуса, причины отклонения и даты создания доступны только для чтения при обычном создании или обновлении через сериализатор.

### 2.2. Проекты

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/projects/` | Получить список проектов |
| GET | `/api/projects/{id}/` | Получить проект по ID |

API проектов доступен только для чтения. Создание, изменение и удаление проектов через эти маршруты не предусмотрены.

### 2.3. История изменений

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/history/` | Получить список доступных событий |
| GET | `/api/history/{id}/` | Получить событие по ID |

История содержит описание события, тип события, связанную задачу, пользователя-инициатора и дату создания записи.

### 2.4. Вспомогательные маршруты

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api-auth/login/` | Вход в интерфейс API |
| POST | `/api-auth/login/` | Отправка формы входа |
| POST | `/api-auth/logout/` | Выход из интерфейса API |

Доступные действия зависят от настроек аутентификации Django REST Framework.

## 3. Создание задачи через REST API

**Маршрут:** `POST /api/tasks/`

**Доступ:** требуется аутентификация.

Пример тела запроса:

```json
{
  "title": "Подготовить отчёт",
  "description": "Описать результаты работы",
  "project": 1,
  "assignee": null,
  "priority": "medium",
  "deadline": "2026-11-15"
}
```

Идентификатор проекта должен соответствовать существующему проекту. Дата указывается в формате `YYYY-MM-DD`. Поле `assignee` можно не указывать, если исполнитель не назначен.

Статус новой задачи и владелец устанавливаются серверной логикой и не должны передаваться как обычные изменяемые поля.

При успешном создании возвращается сериализованное представление задачи.

Возможные ошибки:

- `400 Bad Request` — неверные или отсутствующие обязательные данные.
- `401 Unauthorized` — запрос не прошёл аутентификацию.
- `403 Forbidden` — недостаточно прав для выполнения действия.

## 4. Изменение статуса задачи

**Маршрут:** `POST /api/tasks/{id}/transition/`

**Доступ:** требуется аутентификация.

Пример тела запроса:

```json
{
  "status": "pending"
}
```

Для отклонения задачи можно передать причину:

```json
{
  "status": "rejected",
  "reason": "Не хватает исходных данных"
}
```

Для назначения исполнителя используется поле `assignee` с идентификатором пользователя:

```json
{
  "status": "assigned",
  "assignee": 2
}
```

### Допустимые переходы

| Текущий статус | Допустимые следующие статусы |
|---|---|
| `new` | `pending` |
| `pending` | `assigned`, `rejected` |
| `assigned` | `in_progress` |
| `in_progress` | `done` |

Переходы проверяются сервером. Нельзя произвольно менять статус, обходя установленный бизнес-процесс.

При назначении требуется существующий пользователь. При отклонении требуется непустая причина. Переход к выполнению и завершению доступен назначенному исполнителю согласно логике приложения.

Возможные ошибки:

- `400 Bad Request` — недопустимый переход, отсутствующая причина отклонения или неверный исполнитель.
- `401 Unauthorized` — пользователь не авторизован.
- `403 Forbidden` — действие запрещено для текущего пользователя.
- `404 Not Found` — задача не найдена среди доступных пользователю задач.

При успешном переходе обновляется статус задачи и создаётся запись истории в рамках транзакции.

## 5. AJAX-маршруты интерфейса

Эти маршруты используются веб-интерфейсом и отличаются от стандартных маршрутов REST API. Они принимают POST-запросы и используют данные формы.

| Метод | Маршрут | Назначение |
|---|---|---|
| POST | `/api/tasks/create/` | Создать задачу через интерфейс |
| POST | `/api/tasks/{id}/status/` | Изменить статус задачи |
| POST | `/api/tasks/{id}/delete/` | Удалить задачу |

### Создание задачи

Маршрут: `POST /api/tasks/create/`

Ожидаемые поля формы:

- `title` — название задачи;
- `description` — описание;
- `project` — идентификатор проекта;
- `status` — статус;
- `priority` — приоритет;
- `deadline` — срок выполнения.

Успешный ответ содержит `success: true` и данные созданной задачи. Некорректные значения возвращают ошибку `400 Bad Request`.

### Изменение статуса

Маршрут: `POST /api/tasks/{id}/status/`

Поле формы:

- `status` — новый статус.

Успешный ответ содержит `success: true` и отображаемое название статуса. При неверном статусе возвращается `400 Bad Request`, при отсутствии задачи — `404 Not Found`.

### Удаление задачи

Маршрут: `POST /api/tasks/{id}/delete/`

При успехе возвращается `success: true` и сообщение о результате операции. Если задача не найдена, возвращается `404 Not Found`.

Для AJAX-запросов следует учитывать CSRF-защиту Django и передавать CSRF-токен в соответствии с настройками приложения.

## 6. HTTP-коды ответов

| Код | Значение |
|---|---|
| `200 OK` | Запрос выполнен успешно |
| `201 Created` | Ресурс успешно создан |
| `204 No Content` | Операция выполнена без тела ответа |
| `400 Bad Request` | Некорректные данные или недопустимый переход |
| `401 Unauthorized` | Требуется аутентификация |
| `403 Forbidden` | Действие запрещено |
| `404 Not Found` | Ресурс не найден или недоступен пользователю |
| `405 Method Not Allowed` | HTTP-метод не поддерживается маршрутом |
| `500 Internal Server Error` | Внутренняя ошибка сервера |

Фактический код ответа зависит от конкретного маршрута и результата обработки запроса.

## 7. Проверка API

Для проверки рекомендуется использовать браузерный интерфейс Django REST Framework или инструмент для отправки HTTP-запросов.

Порядок проверки:

1. Запустить сервер командой `python manage.py runserver`.
2. Авторизоваться в приложении.
3. Выполнить GET-запрос к `/api/projects/`.
4. Выполнить GET-запрос к `/api/tasks/`.
5. Создать тестовую задачу через POST-запрос.
6. Проверить ответ сервера и наличие задачи в списке.
7. Проверить переход статуса через `/api/tasks/{id}/transition/`.
8. Убедиться, что события отражаются в `/api/history/`.

Для проверки целостности данных следует проверить, что при недопустимом переходе статус не изменяется, а после успешной операции результат сохраняется в базе данных.

## 8. Ограничения документации

Описание подготовлено по маршрутам и логике текущего проекта StudyFlow. Если маршруты, права доступа или сериализаторы будут изменены, документацию необходимо обновить.

Примеры запросов предназначены для проверки локальной версии проекта. Перед использованием в production необходимо настроить переменные окружения, секретный ключ, разрешённые домены и подключение к базе данных.
